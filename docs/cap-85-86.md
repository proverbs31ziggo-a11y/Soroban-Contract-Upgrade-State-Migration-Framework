# CAP-85 and CAP-86: what the protocol added, and what this framework uses

Protocol 28 ("Adapter") shipped two changes that make a state-migration framework
possible. This document records which parts of each one this repository depends on,
so that the dependency is a fact in the codebase rather than a claim in a README.

Both CAPs are `Status: Implemented` and `Protocol version: 28` in
[`stellar-protocol`](https://github.com/stellar/stellar-protocol).

---

## CAP-85 — Externally managed contract executables

**The problem it solves.** The factory pattern deploys many contract instances that
share one Wasm — a *fleet*. Upgrading the shared Wasm means updating every instance
individually, and if the fleet is larger than a transaction can hold, there is a
window during the rollout in which some instances run the old code and some the new.
The CAP's motivation names the reason that window is unacceptable: an upgrade may
carry a security fix, or may not be backwards compatible with the previous version.

Stellar had no beacon-proxy equivalent, because that pattern depends on `fallback`
or `delegatecall`, which Soroban does not have.

**What it adds.**

* A new contract executable type, `CONTRACT_EXECUTABLE_EXTERNAL_REF`, holding
  `ContractExecutableExternalRef { executable_owner, tag }`. A contract's executable
  can be a *reference* to a contract-data entry owned by another contract, keyed by a
  tag string.
* A host object, `ExecutableTagObject`, which wraps that tag string. It exists only
  to let the protocol validate the entry, and the validation is the useful part:
  * an entry keyed by a tag **cannot be removed**, so a published build cannot be
    made to vanish;
  * on update, the new value **must be the Wasm hash of an already-uploaded Wasm**,
    so a tag can never point at something that does not exist.
* Three host functions: `create_executable_tag`, `create_external_ref_contract`, and
  `update_current_contract_executable_ref`.

### What this framework uses

| Framework item | CAP-85 element | Why |
| --- | --- | --- |
| `fleet::publish` | writing a tag-keyed entry | A tag is a permanent, validated name for a build. |
| `fleet::promote` | updating the tag-keyed entry | One write repoints every instance that resolves through it — the atomic fleet upgrade. |
| `fleet::adopt_executable_ref` | `update_current_contract_executable_ref` | Points this contract's own executable at a tag's build. |
| `fleet::extend_ttl` | the tag entry's lifetime | The entry must not archive. The application cannot restore it, because it does not own its contents. |
| `examples/vault::promote_fleet` | the whole mechanism | Rollback is the same call with the older tag. |

The two validation rules are load-bearing for the framework's guarantees, not just
convenient. "A tag entry cannot be removed" is what lets `fleet::promote` treat a
published tag as a rollback target that will still be there in six months. "The new
value must be an uploaded Wasm hash" is what makes publishing the *currently running*
build a meaningful act: the tag then names exactly the code that is deployed right
now, which is what a rollback needs.

The framework's own cost is one contract-data write per fleet promotion, regardless of
how many instances resolve through the tag. That is the point of the design.

## CAP-86 — Sparse Symbol-keyed map creation and unpacking

**The problem it solves.** `#[contracttype]` structs serialize as a `MapObject` with
`Symbol` keys, through `map_new_from_linear_memory` and
`map_unpack_to_linear_memory`. Those functions validate **strictly**: if the map's
keys are not *exactly* the struct's fields, the contract call **traps**. The CAP's
motivation states the consequence in the same words this repository's README uses:
adding a new field to a struct or removing an unused one "has rendered contracts
unusable after an update".

**What it adds.** Two host functions:

* `sparse_map_new_from_linear_memory` — as `map_new_from_linear_memory`, except that
  key-value pairs whose value is `Void` are **skipped** and never stored.
* `sparse_map_unpack_to_linear_memory` — as `map_unpack_to_linear_memory`, except that
  (a) a key absent from the map yields `Void` rather than trapping, and (b) a caller
  may unpack a **subset** of the map's keys.

`Void` is what a missing key decodes to, and `Void` maps to `None` for an `Option`
field in the SDK's `contracttype`. That single sentence is the mechanism the entire
framework is built on.

### What this framework uses

The framework does **not** call the sparse map functions itself. It depends on their
*behaviour*, which `soroban-sdk` 28 applies by default. The derive in
`soroban-sdk-macros` 28 emits, for every `#[contracttype]` struct:

```
env.sparse_map_unpack_to_slice(map, &KEYS, &mut vals)
```

which is the SDK wrapper over `sparse_map_unpack_to_linear_memory`.

That gives the framework three things:

| Property | Framework use |
| --- | --- |
| A missing key decodes as `None` for an `Option` field | `schema`: an entry written at v1 is readable by v2 code, so code can ship before its state migrates. This is what makes a batched migration possible against a live contract at all. |
| A key the struct has no field for is discarded | `executor::batch`: a migration can read a *newer* shape than the index says it should, which is what makes a replayed batch idempotent (see below). |
| A missing key **traps** for a non-`Option` field | `preflight`, `check`, and `diff`: a new *required* field is a denial, not a warning, because it makes every un-migrated entry unreadable. |

The third row is the framework's central refusal. It is not a style preference: it is
the exact boundary of what the protocol guarantees.

## Why the sparse semantics make idempotency provable

The executor requires `Migration::up` to be idempotent, because a key can be visited
more than once. For renames and type changes, the generated code relies on a *tolerant
shadow struct*: a struct declaring only the keys the migration consumes, each as
`Option<..>`.

The first visit finds the old key present and converts it. Writing the entry back
produces a map without that key. The second visit unpacks the same shadow struct
against a map that no longer has the key — and gets `None`, because that is what
`sparse_map_unpack_to_linear_memory` returns for an absent key. So the conversion does
not run again, by construction rather than by a guard someone has to remember.

Without CAP-86 the second visit would trap, and every rename or retype migration would
have to be exactly-once — which a batched executor cannot offer, because a batch that
fails is retried whole.

## Protocol requirements in practice

Protocol 28 is required. The two halves fail differently, which is worth knowing
before deploying:

* **`fleet`** needs CAP-85 outright. Without it the references do not exist and the
  code does not run.
* **The rest of the crate** calls no host function newer than protocol 26. What needs
  protocol 28 is decoding an entry written by an older schema — which is the point of
  the crate, not an optimisation. On an older protocol the framework compiles and its
  bookkeeping works, but an upgrade has a window in which the new code cannot read the
  old entries: the exact failure this crate exists to remove.

## What the protocol does **not** provide, and this framework adds

Neither CAP helps with the developer-facing problem:

* **Enumerating storage.** Soroban has no primitive — on chain or over RPC — that
  lists a contract's entries; `getLedgerEntries` needs exact keys. A batched migrator
  therefore needs a key source. `soroban_migrate::index` is one: an append-only paged
  list of the keys the contract has written, maintained by the application on its own
  write path.
* **Versioning.** Nothing records which shape an entry is in. `soroban_migrate::version`
  does, in instance storage, and gates reads on it.
* **Batching and resumption.** Nothing chunks a migration across transactions or
  checkpoints it. `soroban_migrate::executor` does, using the atomicity of a single
  invocation as its only correctness argument.
* **Deciding whether a change is safe.** The protocol tells you a missing key is
  `None` for an `Option`. It does not tell you that adding a required field will
  orphan every existing entry, or that removing one will silently discard it.
  `soroban-migrate check` does.

The CAPs removed the blockers. This repository is the part that was left.
